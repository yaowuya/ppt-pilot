# 用户交互与确认协议

## 目的

本协议把需要用户决定的事项变成可执行、可暂停并可恢复的交互。它适用于新建、恢复和修订入口，并保持宿主中立：只描述检查、提问、等待、记录和继续，不依赖任何特定交互工具或调用语法。

核心规则是：**先检查已有信息，只询问仍然重要的未决事项；一次只提出一个实质性问题；推荐不是确认；提出问题后立即停止本轮。**

## 入口与模式规范化

开始任何工作前，先检查用户请求、工作区输入、`ppt-output/` 中的既有运行和相关持久产物。请求或文件已经给出的答案不得再次询问。

- 新运行未显式指定执行策略时，默认并持久化为 `guided`。
- `run.json.mode` 只保存执行策略，值只能是 `guided` 或 `auto`。只有显式指定 `auto` 才进入自动策略；它跳过可选问题和可选批准，但不能因为请求看起来完整就自行推断为 `auto`。
- `resume`／`revise` 是入口动作，不是持久模式。它们先读取目标运行的 `run.json`，保留既有 `run.json.mode`，再恢复或按失效规则修订；只有用户明确要求切换执行策略时才更新该字段。
- `new` 表示创建入口，不是写入 `run.json.mode` 的新值。
- 运行目标无法唯一确定时，使用产物契约定义的工作区级路由状态 `ppt-output/run-selection.json`；不得猜测、覆盖或把选择问题写入任何候选运行。

首次问题也必须可恢复：不存在不持久化的阻塞问题例外。裸入口缺少足够信息生成语义化 `deck_id` 时，先使用宿主既有的安全文件创建惯例新建且不冲突的运行目录；具体临时名称不属于本协议，但不得复用或覆盖既有目录。写入最小 `run.json` 后，先持久化问题，再提出演示意图问题。不能创建安全运行目录时停止并报告原因，不得先提出无法恢复的问题。

### 目标运行选择

`resume`／`revise` 的目标不能唯一确定时，先按[产物契约](artifact-contract.md)原子创建工作区级路由状态 `ppt-output/run-selection.json`：同时保存 `entry_action` 与完整本地 `operation_payload`，不能只保存候选。然后提出其中同一个目标选择问题并停止。不得写入任何候选运行，也不得改变它们的 `run.json.mode` 或阶段。

恢复时先处理该路由状态：`pending` 原样重放；明确答案先写为 `answered` 并保存原话与规范化候选 `decision`；验证候选目录后读取所选运行、保留既有 `run.json.mode`，并执行已保存的入口动作与原始操作载荷。只有所选运行到达下一个持久状态后才删除 `run-selection.json`。崩溃留下 answered 路由状态时继续消费，不重复询问，也不依赖原对话重建修订请求。已有路由状态格式错误、载荷缺失或与新请求冲突时停止，不创建第二份。

## 决策分类

每次进入阶段或收到答案后，都重新构建决策队列：

1. **已明确**：请求或已批准产物已经给出，直接复用，不得再次询问。
2. **可由工作区确定**：通过读取输入、现有运行或既有约束能够唯一确定，直接记录。
3. **可安全默认**：选择可逆、低影响且不需要用户权限的保守默认值，并写入当前产物的 `assumptions`。
4. **必须询问**：不同答案会实质改变受众、行动、内容范围、主张、来源策略、品牌方向或交付；需要联网／机密授权；没有安全默认值；或者属于 guided 强制批准点。

只把第四类加入队列，并按工作流依赖顺序选择最早的一项。问题数量没有固定目标；完整输入可以没有补充问题，信息很少的输入可以经过多轮，但每轮答案后必须重新计算决策队列，不能机械走完固定问卷。

### 工作区偏好档案

`ppt-output/pilot-preferences.json` 是可选的工作区级偏好档案，用于跨运行复用品牌方向和交付偏好。每次 `new`／`resume`／`revise` 开始决策分类前读取一次：

- `schema_version: 1`；全部字段可选：`brand`（颜色、字体栈、logo 与品牌规则）、`style`（preferred_style_id 或唯一显示名）、`audience`（常用受众与期望行动）、`language`、`confidentiality_restriction`（仅限制型策略）、`evidence_policy`、`notes`；
- 优先级固定为：**当前请求明确答案 > 本运行已批准产物 > 偏好档案 > 安全默认值**。偏好命中的决策按"可由工作区确定"处理，不再询问；用户当前请求给出不同答案时以当前请求为准；
- 档案只能记录**限制型**保密策略（例如"内部资料不得外发"）。跨运行有效的网络或披露授权必须是用户明确给出的 standing 授权（记录授权范围与用户原话），否则每次运行仍按权限问题询问；
- 文件缺失时静默跳过；格式错误、不可解码或 `schema_version` 非 1 时披露原因并忽略该文件继续运行，不停止、不写入任何候选运行目录；
- 偏好档案是咨询性输入，不是控制状态：不出现在任何恢复链中，不替代 guided 批准点，也不得覆盖硬质量门。

## 单问题回合

一次只提出一个实质性问题。一个问题可以要求用户用一句完整意图描述同时补全紧密相关的字段，但不得把互不依赖的多个决策塞进同一轮。

有限选择使用 2–4 个互斥选项：

1. 推荐选项排在第一；
2. 每个选项说明会改变什么；
3. 单独说明推荐理由；
4. 明确声明推荐不是确认，不能代替用户回答。

为了让另一个宿主原样重放，有限选择必须把值列表、逐项效果和推荐理由一起持久化：`options` 保存稳定值，`option_effects` 为每个值保存效果，`recommendation` 保存推荐值，`recommendation_reason` 保存理由。收到含义明确的自然语言回答时，同时保留原始 `answer` 并写入规范化 `decision`；有限选择的 `decision` 必须是 `options` 中的值。

没有合理的有限选项时，提出一个开放问题并给出推荐回答格式或在现有证据下可支持的建议；不得虚构用户偏好。收到开放问题答案时只保存原始 `answer`，不伪造 `decision`。答案仍然模糊时，只提出一个聚焦澄清问题，不能自行推断批准。

提出问题前先写入持久等待状态。提出问题后立即停止本轮：不得继续研究、生成后续产物、启动下游阶段或把内部推荐当作明确回答。声称“等待批准”、展示摘要、没有收到反对或保持沉默，都不构成批准。

## 持久等待与恢复

能够创建运行目录后，每个阻塞问题使用 `run.json.pending_interaction`。完整字段、状态和错误处理见[产物契约](artifact-contract.md)。

处理顺序：

1. 把问题及其完整重放元数据写入 `pending_interaction`，状态为 `pending`；
2. 提出同一个直接问题并停止；
3. 收到明确回答后，在一次 `run.json` 写入中把状态改为 `answered` 并保存原始 `answer`；有限选择还保存规范化 `decision`。此时顶层仍保持原阶段，原阶段仍与 `pending_interaction.stage` 一致；
4. 按 `id` 幂等地把答案和决定写入该阶段负责的产物镜像，并准备同一 ID 的权威 `run.json.interaction_history` 记录；重复恢复不得追加重复记录或重复应用修改；
5. 产物写入成功后，对 `run.json` 做单次原子替换：同时更新 `interaction_history`；批准时写入目标阶段并删除原对象；请求澄清时保持原阶段并把 answered 对象替换为一个新的 pending 对象；
6. 重新计算决策队列。

这里的“单次原子替换”表示读者只能看到完整旧状态或完整新状态，不能看到已经推进 `stage` 但仍残留旧阶段交互对象的中间文件。宿主不能保证安全替换时必须停止并保留 `answered` 状态，不得分步推进。

恢复时先处理这个对象：

- `pending`：原样提出同一个问题和完整选项说明，不创建新问题，也不重做上游工作；
- `answered`：使用已保存的 `answer` 和规范化 `decision` 幂等完成尚未完成的产物写入与原子提交，不再询问；
- 字段缺失、阶段不匹配、有限选择缺少规范化决定或状态无效：停止并报告格式冲突，不猜测答案。

## 批准与请求修订的确定效果

三个 guided 批准问题都使用互斥选项 `approve` 和 `request_revision`，并保存 `checkpoint` 与正整数 `approval_attempt`。第 1 次批准问题 ID 为 `<checkpoint>-approval`；修订后再次询问时，从权威历史取下一尝试号，使用 `<checkpoint>-approval-<N>`（N >= 2）。每次都是新的交互与历史键，不得覆盖此前修订事件。收到任一答案后，先按持久等待协议保存 `status: answered`、原始 `answer` 和规范化 `decision`，再执行以下分支。

### `approve`

以下是规范性转移表；实现必须按整行配对，不能只依据散文中的阶段词：

| interaction id | answered stage | normalized decision | committed stage | 同一原子提交的效果 |
|---|---|---|---|---|
| `brief-approval` | `brief` | `approve` | `research` | 冻结 `简报.md`，删除原交互；若存在 `approved`，同步 `approved.brief: true`。 |
| `outline-approval` | `outline` | `approve` | `storyboard` | 冻结 `大纲.md`，删除原交互；若存在 `approved`，同步 `approved.outline: true`。 |
| `anchor-approval` | `anchor` | `approve` | `production` | 确认两页锚点的当前已验证版本，删除原交互；若存在 `approved`，同步 `approved.style: true`。 |

表中 ID 展示第 1 次兼容形式。`checkpoint`、answered stage 和 decision 相同的 `<checkpoint>-approval-<N>` 沿用同一规范性转移；后缀只区分事件，不改变目标阶段。

简报批准后的研究阶段即使选择离线路径也要完成并持久化，之后才能进入大纲。大纲批准后才可创建页面地图和故事板。锚点批准提交前，嵌套文稿状态必须仍为 `manuscript_approved`，否则不得进入生产。

每个批准原子提交还要按交互 ID 写入权威 `run.json.interaction_history`：保存原始答案、`decision: approve`、阶段产物所有者、该已冻结版本的稳定 `artifact_snapshot_id` 和 `status: applied`。这里的冻结是逻辑冻结：后续修改必须通过失效／修订流程产生新版本，不能原地改变该快照所指内容后继续沿用批准。

可选 `approved` 只是在同一提交中保持一致的镜像；顶层 `stage`、`pending_interaction`、`interaction_history` 和质量门仍是权威状态。

### `request_revision`

在回答写入、修订范围尚未分类以及需要澄清的等待期间，保持原阶段，不设置下一阶段，也不把任何 `approved` 镜像改为 `true`。原始请求先保存在 answered 对象中；删除或替换该对象前，按产物契约把权威记录写入 `run.json.interaction_history`，并写入该批准点的阶段产物镜像。

- 回答已经给出具体且只影响当前批准点的改法：按 `interaction_id` 幂等应用修订，重新执行该阶段验证，再用单次原子替换更新权威历史并删除旧对象；仍需批准时把该检查点 `approval_attempt` 加一，创建新 ID 的批准问题，不能复用旧 ID。
- 回答只表示不批准而没有可执行范围：在权威历史中读取该交互已有的 `clarification_index`，没有时使用 `1`，再次澄清时加一；先写 `affected_scope: unresolved`、`status: clarification_pending` 和该索引，再在同一次 `run.json` 原子替换中把 answered 对象替换为新的 `pending_interaction`。新对象固定使用 `kind: question`，ID 为 `<原 id>-revision-clarification-<clarification_index>`。恢复必须复用已保存索引，不能扫描临时文件重新猜测编号。
- 回答具体要求修改上游内容：分类后不再受“保持原阶段”约束，而是按产物契约的规范性失效重入表，在单次原子提交中返回最早受影响阶段、使依赖项失效并重置文稿授权。不能停留在 `anchor` 后只重新询问视觉批准。

恢复看到 `decision: request_revision` 的 `answered` 对象时，按 `interaction_id` 检查 `run.json.interaction_history`，并幂等补写阶段产物镜像后继续上述分支，不重复原批准问题。只有权威记录与产物写入成功，或者澄清问题替换成功后，才能移除原回答。

## 直接视觉修订与优先级

用户在任何视觉阶段直接提出可执行的品牌、主题、构图或页面修订时，即使该指令不来自 guided 批准问题，也必须先分类并持久化，再修改 brief 或 SVG。按[产物契约](artifact-contract.md)创建下一单调 `visual-revision-<N>`，记录 `kind: visual_revision`、原始 `answer`、`normalized_changes`、`affected_scope`、`supersedes`、`status: applied` 和 `artifact_owner`。整套决定镜像到 `theme.json.user_revision_notes`，锚点决定镜像到主题修订记录和受影响锚点 brief，页面决定镜像到 `visual-briefs/<slide-id>.md`；所有镜像都能从权威历史重建。

当前有效视觉契约按以下固定优先级归并：

```text
不可覆盖内容／证据／兼容性规则 > seed defaults > latest deck theme/brand decision > latest scoped slide decision > local patch defect
```

后来的同作用域决定只有在明确替换同一字段，并通过 `supersedes` 指向旧 `<history-id>:<field>` 时，才能使旧规则失效。废弃规则继续保留在 `run.json.interaction_history`，但必须从 active contract 和生成 brief 中排除。页面决定不得影响其他页面，local patch defect 不得改变焦点、层级、主题或内容边界。

若用户指令同时涉及多个层级，先拆成规范化字段并逐项判断作用域与替换关系，再在一次权威历史更新中保存。无法判断规则应共存还是替换、字段作用域不明确、`supersedes` 目标不存在，或历史与 `theme.json.user_revision_notes`／页面 brief 镜像冲突时，先持久化一个直接澄清问题并停止；不得依赖对话顺序猜测，也不得把互斥规则同时送入生成。

事实、来源、主张、大纲或故事板变化不写成视觉修订；它们继续按失效重入表使文稿批准失效。视觉指令的 `patch`／`recompose` 分类和准确输入遵循[生产 QA、恢复与修订契约](qa-and-revision.md)。

## guided 强制批准点

`guided` 有三个不可省略的明确批准点：

- **简报批准必须获得明确回答**：补齐重要决策并展示简报摘要后，询问是否批准进入研究／大纲工作；
- **大纲批准必须获得明确回答**：展示核心论点、受众行动、支撑论点、证明顺序、页数和证据缺口后，询问是否批准制作故事板；
- **锚点批准必须获得明确回答**：展示封面与最困难内容页的真实渲染证据后，询问是否批准视觉方向进入正式生产。渲染不可用时必须披露 `not_rendered`，不得把源文件检查描述成视觉批准。

每个批准点都必须有直接问题、明确回答和实际等待。推荐、推定同意或自动采用第一项都不能放行。

`auto` 跳过这些可选批准并执行同等内部检查，但仍必须询问用户权限或没有安全默认值的决策。

## 条件式问题

以下条件只在确实阻塞时触发，不形成固定问卷：

- **网络与机密**：外部传输或敏感派生查询需要用户权限；安全的本地盘点和离线工作不询问。
- **故事板冲突**：页数、密度、必需内容、来源支持或叙事取舍没有安全默认值时询问。
- **审稿业务决策**：唯一的证据保持型修复可以直接执行；修订会改变核心立场、建议或受众行动时询问。用户选择不能让未解决的 `BLOCKER`／`HIGH` 通过。
- **品牌与主题**：已提供品牌规范时直接复用；guided 缺少安全视觉方向时询问，auto 可以选择合适的内置种子。
- **生产阻断**：两次修复和确定性布局回退都失败，且继续需要删除已批准内容或改变交付取舍时询问；无效 SVG 硬失败不能由用户豁免。
- **恢复与修订**：文件集合、运行目标、审查证据或修改类别无法唯一判断时询问。

## 停止提问

当前阶段同时满足以下条件时停止提问并继续：

- 会实质改变当前输出的决策已经解决；
- 需要用户权限的行为已经获得明确授权，或已选择不披露的安全路径；
- 当前 guided 批准点已经明确通过；
- 没有需要用户承担业务判断的审稿或生产阻断；
- 剩余未知项都具有安全、可逆的默认值且已经记录。

用户明确要求“其余由你决定”时，可以把剩余非权限型偏好按安全默认处理；该授权不能解释为允许外传机密信息。用户明确切换为 `auto` 时更新运行模式，但仍保留权限和无安全默认值的阻塞问题。
